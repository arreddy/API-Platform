API Management Platform

A production-ready, microservices-based platform supporting the full API lifecycle — from OpenAPI specification registration to dynamic proxying, rate limiting, analytics, and developer self-service.

🗂

OAS Management

Register, validate, and version OpenAPI 3.0/3.1 specifications with automated linting and AI scoring.

🔀

Dynamic Proxy Routing

Create gateway proxies with full version history, one-click rollback, and longest-prefix matching.

🔑

API Key Auth

Generate bcrypt-hashed API keys. Raw key shown once. Revocable with per-key rate limiting.

⚡

Rate Limiting

Redis-backed sliding window rate limiting with in-memory fallback and standard response headers.

📊

Analytics

Time series traffic, P99 latency, status distribution — backed by a partitioned PostgreSQL table.

🤖

OAS Analyzer

Spectral linting + GPT-4o AI scoring on every API registration. Best-effort — never blocks.

🎭

Mock Server

OAS-driven fake response generation using Datafaker. Supports inline and proxy-based mocking.

🏢

Multi-Tenancy

All resources scoped by tenant ID. Complete isolation across APIs, proxies, keys, and analytics.

Architecture

The platform is built as a microservices system with a React developer portal, Spring Boot control plane, reactive gateway, mock server, and a stateless Node.js OAS analyzer.

OAS Analysis Pipeline

POST /api/v1/apis (multipart or JSON) │ ▼ OasValidatorService ← parses & validates OAS with swagger-parser │ ▼ ApiRegistryService ← saves Api entity to PostgreSQL │ ▼ OasAnalysisService ← calls OAS Analyzer (best-effort, async) │ ┌────┴────┐ ▼ ▼ Spectral OpenAI gpt-4o (always) (if OPENAI_API_KEY set) │ │ └────┬────┘ ▼ oas_insights (PostgreSQL)

Data Flow

  1. The developer portal sends API registration, proxy creation, and analytics queries to the Control Plane.
  2. The Control Plane stores configuration in PostgreSQL and exposes management APIs.
  3. After registering an API, the Control Plane calls the OAS Analyzer to lint the OAS document and score it with AI. The result is stored in oas_insights and returned in the registration response.
  4. The Gateway consults the Control Plane via internal token to build routing and enforce policies.
  5. The Mock Server reads OAS definitions from the Control Plane to generate fake responses.
  6. The Gateway logs request data into the Control Plane analytics pipeline (buffered, every 5 s or 100 entries).

Gateway Request Pipeline

For each incoming request, the gateway executes these filters in order:

  1. dynamicRouteLocator — matches longest-prefix, rewrites path, sets proxy exchange attribute.
  2. ApiKeyAuthFilter — if authType=api_key, extracts X-Api-Key, calls Control Plane to validate (60s in-memory cache).
  3. RateLimitFilter — sliding window via Redis (rl:{proxyId}:{keyId}:{slot}). Adds X-RateLimit-Limit / X-RateLimit-Remaining.
  4. RequestLogFilter — global, buffers entries, flushes every 5 s or at 100 entries.

API & Proxy Creation Guide

Step-by-step walkthrough for registering your first API and setting up a proxy with policies.

Creating an API

  1. Register Your API

    Navigate to APIs → Register New API in the Developer Portal. Upload an OpenAPI 3.0/3.1 specification file or paste JSON/YAML directly.

    curl# Via file upload
curl -X POST http://localhost:3001/api/v1/apis \
  -F "oas=@petstore.yaml"

# Via JSON body
curl -X POST http://localhost:3001/api/v1/apis \
  -H "Content-Type: application/json" \
  -d '{"oas": {"openapi":"3.0.0","info":{"title":"My API","version":"1.0.0"},"paths":{}}}'

  2. Review OAS Analysis Results

    The registration response includes insights from the OAS Analyzer: Spectral violations and an AI quality score (0–100).

    json{
  "api": { "id": "...", "name": "pet-api", "status": "active" },
  "insights": {
    "spectral": {
      "errorCount": 0,
      "warningCount": 3,
      "violations": [{ "code": "info-contact", "severity": "warning" }]
    },
    "ai": {
      "score": 72,
      "summary": "Reasonable structure but lacks contact info and descriptions.",
      "risks": [],
      "suggestions": []
    }
  }
}

  3. Configure Authentication

    MethodConfig
    API KeyType: API Key · Location: Header · Header: X-Api-Key
    JWTValidate via JWT secret configured in Control Plane

  4. Apply Rate Limiting

    json"policies": {
  "rateLimit": { "enabled": true, "requests": 100, "window": "1m" }
}

Setting Up a Proxy

  1. Create the Proxy

    curlcurl -X POST http://localhost:3001/api/v1/proxies \
  -H "Content-Type: application/json" \
  -d '{
    "name": "petstore-proxy",
    "targetUrl": "https://petstore3.swagger.io/api/v3",
    "pathPrefix": "/petstore",
    "stripPrefix": true,
    "policies": {
      "rateLimit": { "enabled": true, "requests": 100, "window": "1m" },
      "auth": { "type": "api_key" }
    }
  }'

  2. Update the Proxy (auto-versions)

    curlcurl -X PUT http://localhost:3001/api/v1/proxies/<id> \
  -H "Content-Type: application/json" \
  -d '{
    "name": "petstore-proxy",
    "targetUrl": "https://petstore3.swagger.io/api/v3",
    "pathPrefix": "/petstore",
    "stripPrefix": true,
    "policies": {
      "rateLimit": { "enabled": true, "requests": 200, "window": "1m" },
      "auth": { "type": "api_key" }
    },
    "changeNote": "Increase rate limit to 200 req/min"
  }'

  3. Rollback to a Previous Version

    curlcurl -X POST http://localhost:3001/api/v1/proxies/<id>/rollback/<version>

  4. Call Through the Gateway

    curlcurl http://localhost:3000/petstore/pet/1 \
  -H "X-Api-Key: apk_your_key_here"

Configuration Best Practices

Security

  • ✓ Always use HTTPS for backend target URLs
  • ✓ Rotate API keys regularly (every 90 days)
  • ✓ Never expose internal headers in responses
  • ✓ Store OPENAI_API_KEY in a secrets manager in production

Performance

  • ✓ Enable rate limiting on all public proxies
  • ✓ Set appropriate timeout values (30–60 seconds)
  • ✓ Monitor backend response times via analytics

Reliability

  • ✓ Use changeNote on every proxy update for a clear version history
  • ✓ Test rollback before deploying critical policy changes
  • ✓ Log all errors and anomalies

Production Readiness Checklist

  • ✓ Change all default secrets (JWT_SECRET, INTERNAL_TOKEN)
  • ✓ Set DEV_MODE=false on the control plane
  • ✓ Restrict CORS_ORIGIN to known origins
  • ✓ Use a managed PostgreSQL and Redis for reliability
  • ✓ Secure gateway and internal service communication with TLS
  • ✓ Store OPENAI_API_KEY in a secrets manager (Kubernetes Secret, AWS SSM)
  • ✓ Add yearly request_logs partitions in PostgreSQL as needed
  • ✓ Configure HPA thresholds appropriate for your traffic profile

Never hardcode secrets Do not put OPENAI_API_KEY or any credential directly in docker-compose.yml or Kubernetes manifests. Use .env / Kubernetes Secrets instead.
